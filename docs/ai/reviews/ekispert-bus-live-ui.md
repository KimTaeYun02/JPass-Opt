# 실제 버스·도보·프론트 재생 검증 결과

2026-11-14. [검증 계약](../design/ekispert-bus-live-ui.md)에 따라 확인했다.
**버스 실조회·대표 좌표 확인·Google 도보·프론트 재생은 통과했다. 제품 최적화 API의 자동 버스 연결은 아직 구현되지 않았다.**

## 1. 실제 버스 검색

UI 자동완성에서 확인한 이름은 다음과 같다. 이전 진단 문서의 예시 표기와 달랐다.

| 구분 | 전체 이름 | 결과 URL의 웹 정류장 코드 |
| --- | --- | --- |
| 출발 | `金閣寺道／京都市営バス` | `42705` |
| 도착 | `北大路バスターミナル(地下鉄北大路駅)／京都市営バス` | `42682` |

도착 자동완성에는 다른 운영사인 `北大路バスターミナル／京都バス`도 있었다. 운영사 접미사를 생략하면 다른 정류장을 선택할 수 있다.

검색 시각은 `2026-11-14T13:55:05+09:00`이다. [검색 사이트](https://roote.ekispert.net/)에서 첫 결과는 다음처럼 표시됐다.

- 교토 시영버스 204번: `京都市営バス・２０４号・北大路バスターミナル・高野行`
- 출발 14:00, 도착 14:12, 표시 소요시간 **12분**, 편도 **230엔**, 환승 0회
- 버스 아이콘과 출발 `Cのりば` 표시 확인
- 화면 모드 크롤러는 204번·205번·102번·다른 205번 대안 등 **4개**를 추출했다. 이번 네 결과는 모두 12분·230엔이었고 양 끝 정류장 이름·DOM 구조도 일치했다.

웹 UI의 버스 아이콘은 관측했다. 다만 현 CLI의 `BUS_NAME_EVIDENCE_ONLY`는 여전히 노선명의 버스 단서를 뜻하며, 공급자 수단 타입을 새로 출력하도록 바꾼 것은 아니다.

## 2. 브라우저 모드 비교와 발견한 오류

| 실행 | 결과 |
| --- | --- |
| 일반 IAB UI, 운영사 명시 선택 | 실제 결과 확인 |
| 기존 크롤러 `--live --headed` 첫 실행 | 결과 출력 단계에서 Windows cp949의 일본어 인코딩 오류 |
| 출력 수정 후 동일 화면 모드 실행 | `BUS_NAME_EVIDENCE_ONLY`, 대안 4개, 종료 코드 0 |
| 같은 입력·시각의 headless 실행 | `HTTP_403`, 시도 1회, 종료 코드 1 |

진단 CLI의 JSON 출력에 ASCII 이스케이프를 사용해 cp949 터미널에서도 일본어 데이터를 손실 없이 출력하도록 수정했다.
cp949 TextIOWrapper에 실제 일본어 문자열이 있는 응답을 출력하고 JSON으로 복원하는 회귀 검사를 추가했다.
제품 크롤러 자체의 반환값·API·클라우드 설정은 바꾸지 않았다. 403 이후 반복 조회·헤더 위조·접근 차단 우회는 하지 않았다.

이번 결과는 화면 모드에서 재사용 가능하다는 근거다. Linux Xvfb·배포 서버에서도 항상 성공한다는 검증은 아니다.

## 3. 정류장 좌표와 도보

검색 결과에서 각 정류장의 `地図` 버튼을 눌렀고, 열린 Google Maps 핀의 좌표를 확인했다.
지도 카메라 중심(`@...`)과 실제 핀 좌표가 달라 **핀의 위도·경도**를 사용했다.

| 지점 | 핀 위도 | 핀 경도 |
| --- | --- | --- |
| 金閣寺道／京都市営バス | 35.0394864 | 135.7337039 |
| 北大路バスターミナル(地下鉄北大路駅)／京都市営バス | 35.0445133 | 135.7583766 |

이는 정류장 대표 좌표다. 204번 C 승강장까지의 정확한 보행 접근점이나 지하 터미널 출입구를 검증한 값은 아니다.
이 좌표 추출은 이번에 UI에서 확인한 것이며 제품 크롤러에 자동 수집을 구현하지 않았다.

Google Routes WALK는 저장된 제한 키로 **총 2회** 호출했다. 장소 검색·Gemini·공식 Ekispert API는 호출하지 않았다.

| 구간 | 시작·도착 좌표 | 결과 |
| --- | --- | --- |
| 금각사 주변 대표점 → 금각사도 정류장 | `(35.0394,135.7292)` → 위 정류장 핀 | **8분·554m**, 경로점 31개 |
| 기타오지 터미널 → 교토 식물원 주변 대표점 | 위 정류장 핀 → `(35.0484,135.7632)` | **17분·1,221m**, 경로점 61개 |

관광지점은 검증용 공개 대표 좌표이며 Google Place ID·관광지 입구를 새로 검색한 값이 아니다. 대표점과 실제 보행 출입구가 다르면 우회가 발생할 수 있다.

## 4. 제품 좌표 처리에서 끊기는 위치

`route_service.find_route_station`에 실제 정류장명과 버스 노선명을 전달했다.
현재 함수가 사용하는 HeartRails 조회는 두 버스정류장에서 `ProviderResponseError`로 실패했다.
같은 클라이언트로 철도역 `北大路`를 조회하면 정확히 1건이 반환됐다.

즉, 실제 버스 결과를 파싱하더라도 모든 지점 이름을 기존 철도역 좌표 조회로 처리할 수는 없다.
일반 최적화 흐름에는 관광지 주변 버스정류장 후보를 선정하는 기능도 없다.
이번에 확인한 웹 정류장 코드·운영사·지도 대표 좌표를 별도로 보존하는 처리가 필요하다.

## 5. 프론트 재생 확인

실측 도보 2개와 실제 204번 버스 결과를 **진단용 응답**으로 조립했다.
현재 `RouteResponse` Pydantic 모델을 통과한 응답을 별도 FastAPI 앱에서 공급했고,
실제 프론트 어댑터 → 실제 Vite 프록시 → 진단 FastAPI → 실제 파서·렌더러·`mapRoutePaths`를 실행했다.
첫 검증 스크립트의 예상 문자열을 일본어 `42分`으로 잘못 쓴 것은 한국어 출력 `42분`으로 고쳐 재실행했다. 제품 오류가 아니었다.

- 도보 8분 + 정류장 대기 5분 + 버스 12분 + 도보 17분 = **42분·230엔**
- 진단용 출발 13:47 → 정류장 도착 13:55 → 버스 14:00~14:12 → 대표 관광지점 14:29
- 응답의 `walking → transit → walking` 순서와 시간·요금 합계 검증 통과
- 실제 일본어 버스 노선명 렌더링, 거리 554m·1,221m 표시 확인
- 경로점 수 `31 → 2 → 61` 유지: 도보는 실제 경로 굴곡, 버스는 정류장 간 직선 연결
- 1366×900 PC 뷰포트로 진단 페이지를 열어 도보 `#258258` 점선·노선 `#3267d6` 실선과 재생 안내문을 확인했다.

**대기 5분은 UI의 분 단위 시각으로 수동 조립했다.** 현재 크롤러가 반환한 12분에 최초 대기는 포함되지 않았다.
37분(도보+탑승)과 42분(대기 포함)을 혼동하면 안 된다. 제품의 고정 비용 최적화가 대기를 자동 계산한 결과는 아니다.

제품 최적화 핸들러와 정류장 선택 알고리즘은 이 재생 경로에서 호출하지 않았다.
테스트용 장소 ID는 Google Place ID가 아니다. 기존 계약의 `dataSource: live`가 필요한 파서 테스트이므로 외부 안내문과 증거 메타데이터에 재생임을 명시했다.
기존 화면은 버스도 `노선 이동`으로 표시하고 ‘관광지↔역 버스 연결 미지원’ 안내를 유지한다. 버스 전용 뱃지·정류장 용어·대기 항목을 제품에 추가한 것은 아니다.
진단 화면의 지도는 SVG 개략도다. 실제 Google Maps SDK의 버스 도로 경로 표시는 검증하지 않았다.

진단 산출물은 키를 포함하지 않는 무시 경로에 저장했다.

- `.local-run/bus-headed-live.json`, `bus-headless-live.json`, `bus-walk-live.json`
- `.local-run/bus-live-replay.json`, `bus-live-front-result.json`, `bus-live-preview.html`
- `.local-run/bus-live-replay-server.py`, `web/.local-run/verify-bus-live-replay.mjs`

원본 사이트 HTML·인증 정보는 저장하지 않았다. 진단용 서버와 임시 브라우저 탭은 검증 후 정리했다.

## 6. 회귀 검사와 남은 구현

- 백엔드 계약 검사 **67개 통과**. 버스 진단 검사 12개에는 새 cp949 회귀 검사 1개가 포함된다.
- 프론트 검사 **156개 통과**, TypeScript·Vite 프로덕션 빌드 통과
- 현재 작업의 제품 코드 변경은 없으며 진단 CLI 출력과 검사·문서만 수정했다. 기존 미커밋 변경은 유지했다.

다음 구현 순서는 **버스정류장 후보 선정 → 운영사·웹 정류장 코드·좌표 보존 → 도보 이후 탑승 시각·대기 반영 → 최적화 API와 UI 연결**이다.
공식 API를 새로 도입하지 않고도 기존 웹 결과를 재사용할 수 있는 근거는 확보했다.
다만 정상 화면 모드 실행 환경, 정류장·승강장 식별, 사용 조건, 시간표 처리와 자동 연결은 추가 검증·구현 대상이다.

## 독립 검토

Opus 설계 이후 실제 테스트와 출력 오류 수정을 완료했다. 최종 diff·실측 결과·재생 한계·67/156 검사 결과를 전달한 독립 검토는 **VERDICT: PASS / BLOCKERS: 없음**이다. 검토 모델이 테스트를 직접 실행한 것은 아니다.

검토에서 초기 재생 보고서의 누적 POST 2건에 대한 확인을 요청했다. 이는 기대 문자열을 잘못 쓴 첫 실행과 수정 후 두 번째 실행이 각각 1건씩 보낸 누적값이다.
최적화 API 한 호출의 중복 전송이 아니었다. 진단 클라이언트에 호출 전후 카운터 차이가 정확히 1인지 검사하도록 추가하고, 새 로컬 진단 서버로 외부 API 없이 재실행해 통과했다.
같은 인코딩 문제가 다른 CLI에도 있는지 확인했으며, 공식 API PoC 도구는 정류장명·일본어 노선명을 출력하지 않고 코드·숫자·고정 상태만 출력하므로 이번과 같은 재현 조건은 확인되지 않았다. 해당 도구는 변경하지 않았다.
