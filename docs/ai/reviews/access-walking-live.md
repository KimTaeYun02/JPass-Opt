# 도보 포함 실호출 검증과 버스 연결 후속안

검증일: 2026-11-10. 외부 호출은 사용자가 승인한 소규모 검증 범위다. 기존 구현의 자동 계약 검사와 실제 공급자 검증을 구분한다. 이번 작업은 인증 설정과 검증·조사이며 제품 코드를 변경하지 않았다.

## 결과

**Google WALK와 직접 도보의 백엔드→프론트 처리는 확인했다. 철도 포함 실경로 전체의 검증은 완료하지 못했다.**

| 검증 대상 | 결과 | 확인 범위 |
| --- | --- | --- |
| 백엔드 자동 계약 검사 | 45개 통과 | 외부 공급자는 대체. 실제 HTTP·DP·오류 처리 포함 |
| 프론트 자동 검사 | 156개 통과 | 파서·입력·화면 상태·지도 변환 포함 |
| 프론트 프로덕션 빌드 | 통과 | TypeScript + Vite |
| Google WALK 단독 3쌍 | 성공 | 제한된 실제 키로 시간·거리·polyline 디코딩 |
| 금각사·료안지 최적화 | HTTP 200 | 실제 Places·HeartRails·WALK → FastAPI 요청/응답 모델 → Held–Karp |
| 위 실제 응답의 프론트 처리 | 통과 | 실제 파서·결과 HTML 생성·지도 경로 변환. 수동 브라우저 검증은 아님 |
| 금각사·기요미즈데라 철도 포함 | HTTP 502 | 테스트의 headless Ekispert 크롤러가 첫 페이지에서 HTTP 403. 철도 포함 결과 검증 미완료 |
| 센소지·카미나리몬 | HTTP 422 | 접근 도보 조회 전 같은 이름·다른 좌표 후보를 차단하는 기존 제약 재현 |

FastAPI 통합 요청은 `TestClient`를 사용했다. 크롤러는 테스트 중에만 `headless=True`로 호출했으며 운영 코드의 `headless=False`는 변경하지 않았다. 이 403만으로 운영의 Xvfb/화면 모드도 동일하게 실패한다고 단정하지 않는다. 차단 우회나 반복 재시도는 하지 않았다. 실제 응답을 사용한 프론트 검사는 저장된 응답을 파서에 넣었으며, 이 실행에서 Vite 프록시나 브라우저 렌더링을 다시 검증한 것은 아니다. 프록시 연결은 공급자를 대체한 기존 계약 검사 범위다.

## 실측값

단독 요청의 양 끝은 대표 좌표이므로 실제 장소 검색 결과와 출입구가 같다고 가정하지 않는다.

| 단독 WALK | 시간 | 거리 | 경로 점 수 |
| --- | --- | --- | --- |
| 도쿄역 대표점 → 마루노우치 대표점 | 6분 | 409m | 17 |
| 금각사 대표점 → 기타노하쿠바이초 대표점 | 22분 | 1,613m | 47 |
| 기요미즈데라 대표점 → 기요미즈고조 대표점 | 23분 | 1,684m | 65 |

통합 검증은 Google Places에서 실제 선택한 ID·이름·좌표를 요청에 사용했다. 금각사 → 료안지는 `timingBasis: placeTravelOnly`, 직접 도보 26분·1,905m·0엔, 경로 좌표 66점으로 반환됐다. 접근 도보와 직접 도보를 포함해 WALK 14회, 크롤링 0회가 실행됐다. 프론트에서도 동일한 합계·도보 경로 점 수를 확인했다.

금각사·기요미즈데라 검증은 WALK 12회 후 크롤링 1회에서 403을 받았다. 0분이나 도보 결과로 숨기지 않고 안전한 502로 전달했다. 전체 실제 Google 요청은 Routes 29회, Places Text Search 6회다. Gemini는 호출하지 않았다. 이는 호출 건수이며 청구 금액은 별도로 확인해야 한다.

## 인증 설정

- `JPass Opt Web`에서 Routes API 사용 설정을 확인했다.
- 별도 서버 키 `JPass Routes Server Local`을 생성했다. 저장된 제한은 **Routes API 한 개 + 현재 PC 외부 IPv4 한 개**로 확인했다.
- 키는 Git에서 무시되는 저장소 루트 `.env`의 `GOOGLE_ROUTES_API_KEY`에만 저장했다. 키 값·현재 외부 IP는 이 문서에 기록하지 않는다.
- 기존 Places·브라우저 지도 키의 권한은 확장하지 않았다. 배포 환경이나 Kubernetes Secret에는 새 키를 주입하지 않았다.
- 이 키는 현재 PC 검증용이다. 서버 배포 시 서버의 고정 송신 IP와 별도 인증 설정이 필요하다. IP 제한을 해제해서 재사용하지 않는다.
- 직접 백엔드를 실행할 때는 루트 환경 파일을 명시해서 읽어야 한다. `backend` 디렉터리 기준 `uvicorn app.main:app --env-file ../.env`를 사용한다. 단순 `create_app()`은 루트 `.env`를 자동으로 읽지 않는다.

## 드러난 제약: 역 이름만으로는 부족함

HeartRails 실제 응답에서 `浅草`는 운영사별로 다른 좌표를 가진다. `渋谷`도 같은 형태다. 현재 접근 모드는 이 모호성을 422로 차단한다. 이는 예외적인 먼 동명이역만의 문제가 아니므로 일반적인 도쿄 일정에서도 기능을 막을 수 있다.

같은 이름이라고 좌표를 하나로 합치거나 첫 역으로 대체하면, 측정한 접근 도보의 끝과 실제 승차역이 어긋날 수 있다. 내부 좌표 키만 개선해도 이름을 입력하는 크롤러의 승차역 선택까지 보장되지는 않는다. 따라서 이번 검증에서는 가드를 완화하지 않았다. 역 식별자와 실제 출발·도착 교통 지점을 보존하는 공급자 인터페이스를 먼저 정해야 한다.

Opus에는 관련 서비스·HeartRails·크롤러 소스를 제공해 읽기 전용으로 후속 설계를 검토시켰다. 같은 이름·같은 지역에서 좌표 분포가 1km 이내이면 대표 역으로 합치는 안을 제안했지만 채택하지 않았다. 거리 임계값만으로 동일한 승차 지점임을 증명할 수 없으며, 대표 역과 실제 크롤러 선택 지점 사이 이동 비용을 보장하지 못하기 때문이다. 이 검토는 수정 구현의 승인이나 실경로 성공 증거가 아니다.

## 버스 연결 권고안

**Google WALK는 유지하고, 대중교통 공급자를 Ekispert 공식 API로 연결할 수 있는지 먼저 작은 PoC로 확인하는 방향을 권고한다.** 공식 API 계약·키·버스 사업자 커버리지는 아직 확보·실검증하지 않았다. 현재 연결은 Ekispert 웹사이트 크롤러이며 공식 API와 다르다.

1. **역·정류장 식별자 확보:** `geo/station`에서 관광지 근처 철도역과 버스 정류장을 찾는다. `type=train`/`bus.local` 필터와 반환 `Station.code`, `GeoPoint`를 활용할 수 있다. Google 좌표와 맞추려면 요청·응답의 측지계를 `wgs84`로 명시한다. 기본값은 `tokyo`다. [주변 교통 지점 검색](https://docs.ekispert.com/v1/api/geo/station.html), [교통 유형](https://docs.ekispert.com/v1/dictionary/type/)
2. **식별자로 대중교통 조회:** `search/course/extreme`은 `viaList`에 역 코드와 좌표 등을 허용하고, 버스 이용 여부·출발 일시를 지정할 수 있다. 반환 경로의 교통 지점·구간 유형·시간·요금을 우리 모델로 변환하는 어댑터를 검증한다. 해당 지역의 필요한 버스가 실제 반환되는지 확인한 뒤 채택한다. [경로 탐색](https://docs.ekispert.com/v1/api/search/course/extreme.html)
3. **전체 관광지 간 비용 비교:** 직접 도보, 도보→철도→도보, 도보→버스→도보, 도보→버스→철도→도보를 비교한다. 버스가 항상 기존 기준역으로 향하도록 강제하면 유효한 버스 직결 경로를 놓칠 수 있다.
4. **기존 코드 재사용:** 장소 ID·좌표 입력, Google 도보 클라이언트, 유향 비용 행렬, Held–Karp 순서 계산, 구간 목록과 지도 렌더링 골격은 재사용할 수 있다. `station`만 있는 지점 유형, 이름 기반 좌표 조회, `transit`으로 뭉친 교통 구분은 버스 정류장·실제 교통수단·provider ID를 다루도록 확장해야 한다. 프론트가 새 정류장 정보를 직접 만들도록 요구하지 않는다.
5. **시간표 처리:** 먼저 한 쌍의 실제 버스 경로에서 대기·탑승·환승·도착 시각을 검증한다. 현재 DP는 고정 비용 행렬용이므로 그대로 시간표 최적화라고 부르지 않는다. 초기 순서 계산 후 실제 누적 출발시각으로 경로를 검증·재계산하는 단계와, 순서 자체를 시간에 따라 최적화하는 확장을 구분한다.

Google Routes API는 공식 FAQ에서 일본 대중교통 파트너를 지원 대상에서 제외한다. 따라서 일본 버스를 Google WALK의 `TRANSIT` 변경만으로 해결하는 안은 채택하지 않는다. [Google 공식 FAQ](https://developers.google.com/maps/faq#transit_directions_countries)

또한 Ekispert에 관광지 좌표를 직접 넣는 방식의 최근접 역 접근 시간은 직선거리와 분당 80m로 계산된다고 문서에 명시돼 있다. 실제 Google 도보와 이 시간을 중복 합산하지 않도록, PoC에서 접근 구간의 출처와 대체 범위를 분리해야 한다. [좌표 정보](https://docs.ekispert.com/v1/dictionary/coordinate-information/)

다음 구현의 선행 조건은 공식 API 이용 가능 여부·키·대상 지역 커버리지다. 이것을 확인한 뒤 **동명역 식별과 버스 연결을 같은 교통 지점 모델로 해결**하는 편이 현재 크롤러에 버스 이름만 추가하는 것보다 타당하다. 버스 제품 코드는 이번에 구현하지 않았다.
