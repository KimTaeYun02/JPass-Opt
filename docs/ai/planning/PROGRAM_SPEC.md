서비스 목적: **내 여행에 맞는 패스를 추천하고, 그 패스를 더 활용할 수 있는 여행지도 추천한다.**

개인 취미용 소규모 일본 여행 프로젝트이며 PC를 우선한다. 지도는 Google Maps, 장소 인식은 Places, 경로·운임은 검증 후 NAVITIME, 패스 적용 판정은 팀원 RAG가 담당한다. RAG는 관리 문서에서 근거를 검색해 판정하는 모듈이다. 사용자는 방문 순서를 입력하지 않고 반드시 지켜야 할 날짜·시간만 지정한다.

첫 MVP(핵심 가치를 검증하는 최소 기능 제품)는 입력·시간표, 일정·경로, 패스 비교, 추가 여행지 추천이다. 회원가입·결제/예약·협업·장기 저장·모바일 전용UX·자체 경로 엔진은 제외를 제안한다. 지원 지역·패스 목록은 자료·API 커버리지 확인 후 결정하며 일본 전역 지원을 보장하지 않는다.

## 3. 작성·관리 규칙

예시의 상세번호·요구사항ID·요건ID·요구사항명(대분류/중분류)·상세내역·해결방안·필요 산출물·출처·수용여부·변경유형·비고를 사용한다. Excel 병합 헤더는 Markdown 두 열로 풀어 쓴다. FR은 기능, NFR은 성능·보안·운영 등 비기능이다. RC/NRC는 대응 설계·검증 추적ID이며 별도 기능이 아니다.

FR 그룹코드 I/T/P/R/D/O는 입력/시간표/일정·경로/패스/여행지/결과의 업무 영역을 뜻한다. P 영역 안에서 경로 조회·운임·시간 검증·일정 수정으로 대분류를 나눈다.

| 수용여부 | 의미 |
| --- | --- |
| 확정 | 사용자 합의 제품 방향·구현/시험 완료 아님 |
| 제안 | 상세 규칙 초안·사용자/팀원 확인 전 |
| 확정 / 수치 제안 | 방향은 합의·P 수치는 확인 전 |
| 검증 필요 | 실제 응답·계약·자료 검증 후 실데이터 활성화 |

변경유형은 기존 명세 상세화·재분류 ‘재구성’, 새 정책 ‘신규’다. 비고의 A는 테스트, G는 착수 조건, P는 설정값이다. **P-01~P-19는 이번에 선택한 임시값이며 실제 코드·클라우드 설정, 공식 쿼터, 성능 달성·사용 권한으로 해석하지 않는다.** 사용자 숫자 승인과 공급자 이용 허가는 별개다. 이 표가 상세 수치를 정의하고 부록은 흐름·데이터·검증 근거를 보완한다.

p95는 측정값95%가 그 이하인 지점이다. P-19는 미측정 성능 목표이지 보장값이 아니다.

테스트 세션은 서버가 발급한 한 테스트 사용자 식별자로 유지되는 개발 실험 단위다. 페이지 새로고침·작업 변경·대안 검증으로 카운터를 초기화하지 않는다. 새 세션은 개발자가 비용 확인 후 시작한다. 공개 배포의 다중 세션 우회·전체 일/월 예산은 G-06·G-09에서 별도 설계하며120회가 절대 결제 상한은 아니다.

실행 전 필수 조회·재시도·분리 예상 수를 보수적으로 계산해 작업·세션·계약·비용을 확인한다. 완전 검증 수가 상한을 넘으면 입력 수정 또는 ‘일부 검증 실행’을 선택하게 한다. 일부 검증은 고정 일정 연결 구간부터 조회하고 잔여는 예산 미확인이다. 필수 장소·시각을 삭제해 예산에 맞추지 않는다. 알려진 최소 조회조차 감당 못하거나 비용 통제 불가면 요청0건으로 차단한다. 실행 중 추가 조회도 남은 상한을 넘기지 않는다. 전체 새 추천을 자동 시작하거나 상한을 자동 올리지 않는다.

15분 여유는 권장 조건이다. 시각표 기준 고정 방문 시각 안에 도착할 수 있지만 15분을 확보하지 못하면 ‘여유 부족’ 경고를 표시하며 필수 일정 자체를 불가로 판정하지 않는다. 고정 시각보다 늦는 것은 필수 조건 위반이고, 평균 시간만 확보된 경우는 충족 미확인이다. 기한 초과·취소로 종료된 작업의 지연 응답도 현재 결과에 적용하지 않는다.

RAG 배치 1회는 우리 백엔드에서 팀원 모듈로 보내는 요청 수다. 모듈 내부 검색·외부 모델 호출 수와 과금은 이 숫자만으로 제한되거나 보장되지 않으므로 G-05·G-06에서 별도로 합의·계측한다.

추가 여행지도 채택 후 방문지 15곳 상한에 포함한다. 초과하면 채택을 거절하고 입력을 보존하며 외부 요청을 보내지 않는다. 사용자가 다른 장소를 직접 제거한 후 다시 채택할 수 있다. 보유 자료의 위치가 이미 확정돼 있으면 불필요한 Places 상세 조회를 하지 않으며, 추가 확정이 필요하면 P-14 남은 한도 안에서만 조회한다.

재사용 키는 출발·도착·방향·날짜·출발/도착 시각 기준·교통수단·옵션·정밀도·조회 버전을 포함한다. RAG 결과는 패스 자료 버전도 검사한다. 공급자별 허가·보관·표시 조건을 따로 적용하며 NAVITIME 허가가 Google·RAG 허가를 대신하지 않는다.

### 비용 중단

사용자의 기존 지시인 ‘결제금액 KRW 1,000 초과 시 즉시 종료’를 유지한다. 확인된 청구액이 이를 초과하면 비용 발생 작업을 중단한다. 한도 내 사용을 확인·통제할 수 없을 때도 추가 유료 실험을 보류한다.

이 한도는 여행 교통비가 아니라 개발 중 API 이용 결제금액에 적용한다. 원화 청구액 또는 결제 제공자가 확인한 원화 환산액을 기준으로 한다. 외화 청구만 확인되고 환산 기준·수수료를 포함한 한도 내 사용을 확인할 수 없으면 추가 유료 실험을 보류하며 임의 환율로 안전하다고 판정하지 않는다.

테스트 단계의 확인 책임자는 실험을 실행하는 개발자다. 각 API 실험 배치 실행 전후에 서비스별 요청 수와 비용·청구 현황을 확인한다. 집계 지연을 비용 0원의 증거로 사용하지 않는다. 확인 가능한 쿼터·예상 비용으로 한도를 통제할 수 없는 배치는 실행하지 않는다. 공개 배포 시 비용 확인 주기와 차단 담당자는 별도 확정한다.

호출 쿼터와 예산 알림은 실시간 원화 결제 상한을 보장하지 않는다. 서비스별 사용량, 예상 비용과 실제 청구 확인을 함께 사용하며, 추가 계약·한도 증가·유료 기능 활성화는 별도 승인을 받는다. 이 명세 작성 중에는 유료 API 조회나 클라우드 설정 변경을 하지 않는다.

## 부록 B. 사용자 태스크

상태: 장소·고정 일정 입력과 패스·추가 여행지 추천이라는 흐름은 확정이다. 후보 생성, 수정 적용 및 외부 연계 절차는 제안이다.

1. 여행 시작일과 종료일을 입력한다.
2. 장소를 검색해 정확한 장소명·주소를 확인하고 목록에 추가한다.
3. 장소별로 꼭 방문 / 시간이 남으면 방문을 선택한다.
4. 날짜 자유, 날짜만 고정, 날짜와 시간 고정 중 하나로 배치한다. 방문 순서를 별도로 입력할 필요는 없다.
5. 필요하면 입국·출국 장소와 시각, 숙소, 비용·시간 선호를 추가한다.
6. 명시적으로 추천 실행 버튼을 누른다. 프로그램은 입력을 검증하고 제한된 일정 후보를 만든다.
7. 필요한 구간만 NAVITIME으로 조회하고, 경로·운임 데이터를 정규화한다. 정규화는 공급자별 응답을 공통 데이터 형식으로 바꾸는 작업이다.
8. 같은 경로 정보를 팀원의 RAG에 전달해 패스 후보와 미구매안을 비교한다.
9. 사용자는 일정, 이동 경로, 비용 근거, 추천 패스와 적용되지 않는 구간을 확인한다.
10. 선택한 패스와 남은 시간에 맞는 추가 여행지 후보를 확인한다.
11. 일정을 수정하면 결과를 ‘재검토 필요’로 표시한다. 재사용이 허용된 경우에만 수정 적용 시 영향받는 구간을 검토·재조회한다. 허가가 미확인 또는 불허이면 7절과 부록 E에 따라 변경 입력 전체로 새 추천을 실행하거나 예산 초과 시 보류한다.

필수 일정이 성립하지 않으면 원인을 보여주고 수정을 요청한다. 필수 장소를 삭제하거나 고정 시간을 옮긴 결과를 정상 추천으로 출력하지 않는다.

## 부록 C. 입력·시간표 상세

상태: 순서 없는 장소 입력, 세 가지 시간 제약과 좌표 비노출은 확정이다. 기본 2시간·30분 조절은 현재 프로토타입 값을 유지하는 P-03·P-04 제안이며 사용자 확인 대기다. 나머지 세부 입력·검증·표시 규칙도 현재 구현을 기준으로 한 제안이다.

| 항목 | 필수 여부 | 의미·규칙 |
| --- | --- | --- |
| 여행 시작일·종료일 | 필수 | 종료일은 시작일보다 빠를 수 없다. |
| 방문 장소 | 필수 | 한 곳 이상. 실제 사용 데이터는 검색 결과에서 확정한다. |
| 방문 우선순위 | 장소별 필수 | 꼭 방문 / 시간이 남으면 방문. 현재 프로토타입은 꼭 방문을 한 곳 이상 요구한다. |
| 시간 제약 | 장소별 필수 | 날짜 자유 / 날짜만 고정 / 날짜와 시간 고정. |
| 예상 체류시간 | 장소별 | 새 장소의 기본값 120분. 방문 시간을 뜻하며 이동 시간을 포함하지 않는다. |
| 도착·출발 장소·날짜·시간 | 선택 | 이동 범위와 시작·종료 조건. 시간 입력 시 날짜가 필요하다. |
| 숙소 | 선택 | 하루의 시작·종료 지점 후보. 미입력 시 임의의 숙소를 가정하지 않는다. |
| 여행 선호 | 선택 | 비용 절약 / 균형 / 이동 시간 단축. 현재 기본값은 균형. |

### 시간표 조작

- 날짜를 가로축, 시간을 세로축으로 배치한다. P-05대로 현재는 5일 단위로 표시한다.
- 장소 카드를 시간 칸에 놓으면 해당 날짜와 시작 시간을 고정한다.
- 날짜 제목 또는 날짜만 고정 영역에 놓으면 시간 고정을 해제하고 날짜만 고정한다.
- 날짜 자유 영역으로 되돌리면 날짜·시간 고정을 해제한다. 체류시간은 보존한다.
- 이미 배치한 블록을 이동해도 체류시간과 장소 정보는 보존한다.
- 위쪽 끝을 당기면 종료 시간을 고정한 채 시작 시간을 조절한다. 아래쪽 끝은 반대로 동작한다.
- 방문 시간은 30분 단위, 최소 30분이다. 현재 허용 범위는 하루 안의 30~1,440분이며 자정을 넘는 방문은 거절하고 사용자가 날짜별로 나눠 입력한다. 자동 분할 기능은 없다.
- 일반 보기 08:00~22:00와 전체 보기 00:00~24:00를 제공한다. 화면 범위 안에서 블록 길이를 유지하도록 드롭 위치를 보정한다. 블록이 표시 시간 범위보다 길면 드롭을 거절하고 기존 입력을 보존하며 전체 보기에서 배치하도록 안내한다. 보기 전환만으로 기존 방문 시간을 변경하지 않는다.
- 겹치는 배치·잘못된 드롭·취소는 원래 일정을 보존한다. 클릭 또는 Enter로 편집창에서도 수정할 수 있다.
- 여행 기간 축소로 범위 밖이 된 장소는 경고 영역에 보존한다. 자동 삭제·자동 날짜 변경은 하지 않는다.
- 모든 입력 시각은 일본 현지 시간으로 해석한다. 교통편의 실제 분 단위 시각을 방문 입력의 30분 간격에 맞춰 반올림하지 않는다.

현재 도착·출발·숙소는 텍스트 입력이다. 실제 경로 생성에 사용하려면 검증된 장소 좌표로 연결하는 추가 구현이 필요하다.

```text
       ├─ 일정 조정·호출 예산·오류 처리
       ├─ NAVITIME 어댑터: 경로·운임 → 공통 형식
       ├─ 팀원 RAG: 패스 문서 기반 비교·근거
       └─ 보유 여행지 목록: 추가 방문 후보
```

Google Routes는 현재 계획의 대중교통 경로 공급자로 사용하지 않는다. NAVITIME이 필요한 범위를 충족하지 못하면 명세를 갱신하고 대체 공급자 또는 서비스 범위를 결정한다. NAVITIME이 JR 패스 전체의 최종 적용 판정을 대신한다고 가정하지 않는다.

백엔드를 구현할 경우 NAVITIME 및 RAG의 비공개 인증 정보는 서버에만 두는 것을 필수 보안 조건으로 제안한다. 브라우저에는 지도·Places용 제한 키만 사용한다. 실데이터의 RAG/외부 모델 전달은 이용 허용 범위 확인 후 활성화한다.

## 부록 E. 데이터·인터페이스

상태: 전체가 인터페이스 제안이다. 외부 응답·보관·전달 범위는 검증 필요다.

아래는 내부 공통 형식의 제안이다. 현재 TypeScript 모델이나 NAVITIME의 실제 응답 스키마를 그대로 기술한 것이 아니다. 금액은 JPY 정수 또는 null, 날짜·시간은 시간대가 명시된 형식으로 전달한다.

| 데이터 | 필수 내용 |
| --- | --- |
| TripInput | 입력 버전, 여행 기간, 확정 장소, 우선순위, 시간 제약, 체류시간, 검증된 선택 도착·출발·숙소, 여행 선호 |
| RouteLeg | 내부 구간 ID, 출발·도착 장소 ID, 검색 날짜·시각·조건, 공급자 경로·구간 ID(null 허용), 운영사·노선·열차, 이동시간, 시간 정밀도, 조회 기준 시점, 구간 검증 상태·사유 |
| FareItem | 운임 계산 단위 ID, 관련 구간 ID 목록, 금액 또는 null, 일반 운임/특급요금 등 종류, 검증 상태 |
| PassEvaluation | 입력·경로·패스 문서 버전, 패스 ID·가격·사용일, 구간별 적용 판정, 잔여 요금, 총액·절감액, 총액 검증 상태·사유, 근거 문서와 해당 위치 |
| DestinationSuggestion | 장소 ID·명칭·위치 정보, 패스 적용 근거, 예상 체류·이동시간, 추가요금과 일정 성립 여부의 검증 상태 |

판정은 `covered / uncovered / unknown`, 금액은 `verified / estimated / unknown / failed`, 시간 정밀도는 `timetable / average / unknown`처럼 명시적으로 구분한다. 총액 검증 상태는 `passed / incomplete / failed`이며 각각 검증 완료, 구성요소 미확인, 합계 불일치 등 검증 실패를 뜻한다. 검증 상태와 사유는 프로그램이 산술 검증 후 기록하며 RAG의 적용 판정을 대체하지 않는다. `unknown`과 `failed`를 0원 또는 통과로 변환하지 않는다. 문서 버전은 어떤 패스 자료에 근거했는지 식별하는 값이다.

RouteLeg의 구간 검증 상태도 `verified / estimated / unknown / failed`로 구분한다. 사유는 `budget / deadline / no_route / provider_error / permission / missing_data` 등 명시적인 코드와 설명이며 완료 시 사유는 null이다. 미조회·미완료 구간은 내부 ID와 사용자 장소·검색 조건만 유지하고 공급자 ID·운임·이동시간을 만들어 넣지 않는다. 구간 미확인은 RAG에 전달할 때도 그대로 유지하며 패스 적용이나 전체 일정 성립을 확정하지 않는다.

시간 정밀도가 `average`이면 시간 제약을 포함한 구간 검증 상태는 `estimated` 또는 `unknown`이며 `verified`로 표시하지 않는다. 운임 자체의 검증 상태는 별도다. `timetable`도 모든 필수 데이터·시간 제약 검증을 통과하기 전에는 구간 검증 완료를 뜻하지 않는다.

### 백엔드 인터페이스 제안

| 인터페이스 | 역할 |
| --- | --- |
| `POST /api/plans` | 입력 스냅샷을 검증해 호출 예산 안에서 일정·경로 후보 생성 |
| `POST /api/plans/revise` | 재사용 허가 시 승인 결과·변경 입력 영향 분석. 미확인/불허이면 이전 공급자 결과 없이 전체 새 추천 또는 예산 부족 보류 |
| `POST /api/passes/compare` | 공통 경로·운임 정보를 팀원 RAG에 전달해 비교 결과 반환 |
| `POST /api/destinations/suggest` | 패스·일정 문맥으로 보유 목록에서 후보 검색. 외부 경로 조회 없음 |

재조회에는 사용자 입력, 검색 조건, 입력 버전을 포함한다. 공급자 응답이나 재사용 토큰을 클라이언트가 보냈다는 이유만으로 신뢰하지 않는다. 보관 권한이 없으면 이전 응답을 서버에 저장하는 방식은 사용하지 않는다. 구체적인 수치 예산은 P-09~P-13을 따른다.

보관·재사용이 허용되지 않는 계약에서는 부분 재사용 수정 모드를 비활성화한다. `revise`는 이전 공급자 결과를 이용하지 않고 변경된 사용자 입력 전체로 새 추천을 실행하는 모드로 제한한다. 실행 전 추가 조회 필요성을 안내하고 예산을 확인한다. 새 조회가 예산을 초과하면 실행하지 않고 수정 입력과 재조회 필요 상태만 보존한다. 표시 자체의 권한까지 확보되지 않으면 실제 데이터 연계 기능을 비활성화한다.

구체적인 요청·응답 JSON, 비동기 작업 방식과 RAG 오류 형식은 팀원과 확정한다.

### 공식 문서에서 확인한 제약

- `train_data=average`가 기본이며 `timetable`은 별도 옵션 계약이 필요하고 API 마켓에서는 이용 불가로 명시되어 있다. 이는 시각표 기반 기능의 착수 조건이다. [NAVITIME 경로 검색 / train_data](https://api-sdk.navitime.co.jp/api/specs/api_guide/route_transit.html)
- 같은 명세는 경유지·체류시간 입력을 제공하며, 체류시간 `stay-time` 범위를 0~300분으로 명시한다. 따라서 UI의 긴 체류시간을 API 경유지 한 번 요청에 그대로 넣지 않고 분리 조회 가능성을 검증한다. [NAVITIME 경로 검색 / 地点のJSON表現](https://api-sdk.navitime.co.jp/api/specs/api_guide/route_transit.html)
- `fare_break` 설명에는 환승할인으로 앞 구간 운임이 다음 구간에 합쳐져 출력되는 사례가 있다. 단순 합산 금지의 근거다. [NAVITIME 경로 검색 / FareBreak](https://api-sdk.navitime.co.jp/api/specs/api_guide/route_transit.html)
- 기능·요금·호출 제한은 계약 경로와 상품별로 다르다. 일반 문서의 숫자를 실제 계정에 그대로 적용하지 않는다. [NAVITIME API 목록·요금](https://api-sdk.navitime.co.jp/api/specs/description/about_navitime_api.html)

확인 기준일은 2026-10-10이다. 문서는 이용 허가 자체를 대체하지 않는다.
