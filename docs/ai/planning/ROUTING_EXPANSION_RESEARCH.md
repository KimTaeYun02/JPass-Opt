# 10개 이상 방문지 및 비용 최적화 확장 조사

확인일: 2026-10-14. 운영 코드는 변경하지 않았다. 실경로 조회는 0회이며, 성능 측정에는 직접 생성한 가상 비용표만 사용했다.

## 결론과 개발 순서

실데이터 확보·저장·재사용 범위를 공급자와 확인하는 작업을 병행하면서, 가상 데이터로 다음 순서대로 개발한다.

1. 현재 Held–Karp DP를 유지하고 12개까지의 입력·정확성·성능 검증을 추가한다.
2. 최단시간 / 최저요금 / 시간·요금 가중합 목적함수를 추가한다.
3. 역 쌍별 복수 경로와 운임 구성요소를 표현하는 입력 스키마를 추가한다.
4. 여행 전체에 유효한 단일 패스 시나리오를 비교한다.
5. 날짜별 방문지 배정·숙소 출발/복귀·패스 유효기간·복수 패스를 별도 확장한다.

12개 지원은 하나의 방문 순서를 계산하는 범위다. 여러 날짜에 방문지를 배정하는 기능까지 완료됐다는 뜻은 아니다.

## 데이터 이용 정책

### Web판 크롤링

[공식 Web판 이용약관](https://roote.ekispert.net/help/terms)의 제6조는 다음을 규정한다. 현재 공개된 약관의 개정일은 2024-09-30이다.

- 제6조 (1): 서비스 콘텐츠 전체 또는 일부를 다른 웹사이트·앱 내부에 표시하는 행위를 금지한다.
- 제6조 (3): 약관에서 명시적으로 허용한 경우를 제외하고 복제·옮겨 적기·추출·가공 등의 이용을 금지한다.
- 제6조 (5): 서비스 내용의 2차 이용을 금지한다.

따라서 별도 허용 없이 Web판을 크롤링해 경로 최적화 입력으로 가공하거나 앱에 재사용하는 구조는 약관상 허용된다고 전제할 수 없다. 문제는 장기 캐시뿐 아니라 추출·가공·2차 이용에도 걸린다. 캐시를 5분으로 제한하거나 메모리에만 두는 것이 공개 약관의 예외라는 근거는 확인되지 않았다. 앞선 캐시 재사용 추천의 전제를 정정한다.

이것은 공개 약관에 대한 해석이며, 모든 사실관계에서의 법적 위법성 판단과 같지는 않다. 기존 사용자 파일을 삭제하거나 변경하지 않았다.

### 공식 API

[공식 API 이용약관](https://docs.ekispert.com/v1/WebService_TOS.pdf)은 Web판과 별개다. 확인한 PDF는 2025-12-15 개정본이다. 제1조 2항(2쪽)은 서면 특약의 우선 적용을, 제17조 1항(5쪽)은 이용할 서비스 종류·내용을 개별 계약에서 정함을, 제27조 1항 (4)(7쪽)은 신청서에 기재한 범위·목적·방식과 다른 이용의 금지를 규정한다. 공개 문서에서 경로 결과를 언제나 무기한 저장·사용자 간 공유할 수 있다는 포괄적 허용은 확인하지 못했다.

확인할 계약 범위: 앱에서 최적화 입력으로 가공·표시, 요청 내 결과 사용, 수정 후 재계산, 사용자별 저장 기간, 사용자 간 공통 캐시, 계약 종료 후 보관. 현재 `QuoteProvider.reuseAllowed`는 기술적인 공급자 설정일 뿐 약관상 허용을 증명하지 않는다.

API 약관 제27조 1항 (6)(7쪽)은 출력 데이터의 AI 개발·기능 확장·학습 이용도 금지한다. API 결과를 LLM에 전달하는 기능을 추가하려면 해당 범위도 확인해야 한다. 로컬 DP와 LLM 이용을 동일한 것으로 단정하지 않는다.

[공식 플랜 비교](https://api-info.ekispert.com/plan/)의 주석 1에 따르면 무료 플랜은 경로 검색 결과를 Web판 URL로 반환한다. 무료 플랜에서 구조화된 전체 경로 JSON을 받을 수 있다고 전제하면 안 된다. 주석 2에 따르면 리퀘스트 수 구매형은 평균 대기시간 탐색만 제공하고 다이어그램 기반 탐색은 제공하지 않는다. 시간 의존 탐색을 하지 않는 현재 모델에서 평균 대기시간 방식은 검토 가능한 데이터 공급 선택지지만, 기존 크롤링 `time`과 동일한 수치는 아니므로 혼용하지 않는다.

API 문서의 DNS TTL 60초는 DNS 캐시 설정이다. 경로 결과 재사용 허용 기간이 아니다.

## 현재 구현과 규모 측정

- `web/src/route-optimizer.ts`: `MAX_ROUTE_STOPS = 8`, 완전한 방향별 비용표 검증.
- `web/src/route-dp.ts`: `(방문 집합, 마지막 장소)` 상태에 상위 1~3개 경로를 보관하는 Held–Karp DP. 현재 비교 순서는 시간 → 운임 → 장소 ID 순서다.
- `web/src/route-candidates.ts`: 같은 제한 상수를 사용하지만 오류 메시지에 `2~8`이 직접 적혀 있어 제한 변경 시 함께 수정해야 한다.
- 가중치 비교는 검증용 코드에만 존재하고 운영 DP에는 아직 없다.

현재 계약은 시작·종료 장소 자유, 각 장소 한 번 방문, 복귀 없음이다. 역 사이의 제공된 `time`을 그대로 쓰며 관광지 접근 도보·체류시간을 목적함수에 더하지 않는다. 입력 시간에 이미 포함된 대기시간도 임의로 빼지 않는다. 다일 패스 확장 때문에 시간 의존 탐색을 기본 DP에 다시 도입하지 않는다.

다음은 `tmp/benchmark-route-scale.mjs`로 Node 22.20.0에서 측정한 결과다. 공개 함수의 8개 입력 검증을 우회해 내부 DP만 조사했다. 각 경우마다 새 프로세스로 1회 실행했으며 시작 직후의 실행이다. UI·입력 검증·복제·네트워크는 제외한다. 정확성 검증이나 운영 지원 완료를 의미하지 않는다. 메모리는 Node 런타임을 포함한 프로세스 최대 RSS다.

| 방문지 | 필요한 방향별 비용 항목 | DP 상태 | 최상위 1개 시간 | 상위 3개 시간 | 상위 3개 최대 RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 | 90 | 5,120 | 9.0ms | 10.2ms | 55.6MiB |
| 12 | 132 | 24,576 | 22.5ms | 29.8ms | 81.2MiB |
| 15 | 210 | 245,760 | 126.6ms | 372.5ms | 214.7MiB |

원본 결과는 `tmp/route-scale-benchmark-result.json`에 있다.

10~12개에서 알고리즘 교체를 요구할 만한 성능 문제는 이 측정에서 나타나지 않았다. 우선 12개를 정식 검증하고, 15개부터 브라우저·서버의 반복 측정과 메모리 한도를 따로 정하는 것이 적절하다. 기본 Held–Karp의 시간 복잡도는 O(n²·2ⁿ), 저장 상태 수는 O(n·2ⁿ)이다. 현재 상위 경로 객체·문자열·역추적 참조·BigInt 검증이 실제 메모리 상수를 키운다. [Stanford 강의 자료 2.2절, 2쪽](https://web.stanford.edu/~meghas/resources/cs254.pdf)

12개 지원의 수용 기준:

- 공개 진입점과 후보 계산이 모두 10·12개를 받아들이고, 제한 초과 입력은 명확히 거부한다.
- 작은 무작위 비대칭 비용표에서 최상위 1~3개가 독립 완전탐색과 일치한다.
- 10·12개는 최적해를 알 수 있는 비용표와 동일 비용·역방향 상이·동일 역의 별도 장소 사례를 검증한다. 12! 완전탐색을 일반 테스트로 실행하지 않는다.
- 중복 ID·누락 방향·안전 정수 초과를 기존처럼 거부한다.
- Node 및 실제 브라우저에서 반복 실행시간·메모리·UI 반응성을 측정한다. 필요한 경우 Web Worker로 계산을 이동한다.

## 비용 목적함수

기존 기본값은 유지하면서 목적함수를 매개변수로 추가한다.

- fastest: 시간 → 운임 → ID 순서.
- cheapest: 운임 → 시간 → ID 순서.
- weighted: `score = timeValueYenPerMinute × timeMinutes + feeYen`, 이후 시간 → 운임 → ID 순서.

예를 들어 1분의 가치를 20엔으로 정하면 `score = 20 × time + fee`다. 시간과 요금의 단위를 명확하게 연결한다. 가중치는 0 이상이고 전부 0인 설정은 거부한다. 정수 또는 고정소수점으로 표현하고 가중합의 안전 정수 범위도 검증한다. 원래 분·엔 값과 점수는 따로 반환한다.

각 구간 비용이 고정·가산적이면 상태 `(mask, last)`를 늘리지 않고 같은 DP의 비교 기준을 바꿀 수 있다. 가중치를 바꿀 때 이전의 시간 기준 상위 3개만 재정렬하는 것은 틀릴 수 있으므로 전체 DP를 다시 실행한다.

현재 구간당 한 경로만 주어지는 JSON으로도 '주어진 비용표 내 최저요금 방문 순서'는 계산할 수 있다. 그러나 실제 대중교통 대안을 모두 포함한 최저요금 코스를 보장하지는 않는다. 예를 들어 A→B의 30분·500엔 경로만 입력돼 있으면 40분·200엔 경로를 선택할 수 없다.

## 복수 경로와 패스용 요금 데이터

현재 스키마를 그대로 받고, 확장 입력에서는 `(from, to)`마다 `alternatives[]`를 표현한다. 각 대안에는 `time`, 기본 전체 `fee`, 경로, 안정적인 운송사·노선 식별자, 열차·좌석 종류, 요금 구성요소와 적용 구간이 필요하다. 기본 운임·특급/좌석 추가요금을 분리한다. 전체 요금을 역별로 균등 분배하거나 노선 이름만 보고 JR 구간을 무료 처리하지 않는다.

[공식 경로 탐색 API](https://docs.ekispert.com/v1/api/search/course/extreme.html)는 최대 20개의 응답 경로, 요금·시간 정렬과 탐색 건수를 제공한다. 한 요청에서 여러 후보를 받을 수 있어 후보 수가 곧 호출 수는 아니다. 다만 요금 정렬도 먼저 탐색된 후보들을 정렬하는 방식이며 모든 실제 경로의 최저요금을 보장한다고 해석하지 않는다. [공식 정렬 설명의 탐색 조건 3](https://docs.ekispert.com/v1/tips/sort-route-by-fast-cheap-easy/)

고정 가중치·고정 패스 시나리오에서는 각 역 쌍의 대안에 점수를 매기고 최선의 대안을 골라 DP 비용표를 만든다. 별도 제약이 없다면 방문 순서 최적화와 각 구간의 대안 선택을 이렇게 분리할 수 있다.

패스 미적용 상태에서 시간·요금 모두 열등한 대안도 패스 적용 후에는 이길 수 있다. 그러므로 패스 적용 전 기본 요금만으로 대안을 제거하지 않는다. 패스 적용 시나리오별 지배 관계를 확인하거나 적용 범위가 다른 대안을 보존한다.

패스 정보에는 가격뿐 아니라 적용 회사·노선·구간, 제외 열차·좌석, 적용되는 운임/추가요금 항목, 유효기간의 기준과 사용 자격, 이미 소유했는지가 필요하다. JAPAN RAIL PASS의 NOZOMI/MIZUHO는 별도 티켓이 필요하며 일부 타사 구간도 추가 요금이 발생한다. [공식 사용 조건](https://japanrailpass.net/en/use/conditions-for-use/)

첫 패스 구현은 여행 전체가 패스 유효기간 안에 있다는 조건을 명시하고 다음 시나리오를 비교한다.

1. 패스 없음: 원래 구간 요금으로 DP.
2. 패스 P: P의 적용 규칙으로 남은 구간 요금을 계산하고 DP.
3. 각 결과에 패스 구매비를 딱 한 번 더해서 비교. 이미 보유한 패스는 추가 구매비 0. 가중합에는 구매비의 요금 가중치도 적용.

시간상 만료·활성화 선택이나 여러 패스 구매는 이 첫 단계의 범위 밖이다. 주어진 `time`의 의미는 계속 유지한다.

## 다일 배정과 숙소

먼저 입력 계약을 결정한다: 여행 일수, 방문 날짜 고정 여부, 하루 방문 수 또는 시간 제한, 날짜별 출발·종료 역, 숙소 고정 여부. 하루 시간 제한을 선택하면 체류시간은 그 제한의 검증에 사용할 수 있으나 이동시간 최소화 목적함수와 구분한다.

정확한 다일 배정이 필요하다면 각 방문 집합 S의 하루 최적 비용 `dayCost[S]`를 계산하고, 날짜별로 집합을 배정하는 분할 DP를 추가할 수 있다. 일반 부분집합 분할은 대략 O(days·3ⁿ)이라 현재 단일 순서 DP와 별도로 규모를 평가해야 한다. 전체 최적 순서를 먼저 만든 뒤 적당히 자르는 방식은 편리한 초기 후보지만 다일 최적해를 보장하지 않는다.

숙소가 주어졌으면 날짜별 숙소 출발·복귀 비용을 하루 비용에 반영한다. 숙소 추천 범위는 후보 호텔 목록이 아니라 역/공간 단위의 비용 분포를 구하는 후속 문제다. 현재 데이터에 좌표나 인접 정보가 없으므로 지도 범위 추천까지 계산할 수 있다고 주장하지 않는다.

## 호출 수와 수정·재계산

DP 핵심 함수는 외부 호출을 하지 않는다. n개 장소의 모든 방향별 비용을 개별로 받아야 한다면 항목 수는 n(n−1)이다. 이 표의 90·132·210은 비용 항목 수이며, 재시도·역 코드 확인·후보별 별도 검색 등을 포함한 실제 네트워크 요청 수와 같다고 보장하지 않는다.

공급자가 결과 사용·재사용을 허용하고 조건과 데이터 버전이 유지된 경우에만 다음 절감이 가능하다.

- 완전한 비용표가 있는 상태에서 가중치만 수정: DP 재계산, 추가 조회 0회.
- 장소 한 개 추가: 새 장소와 기존 n개 사이의 양 방향 2n개 항목 추가.
- 장소 한 개 교체: 해당 장소와 나머지 사이의 2(n−1)개 항목 교체.
- 장소 삭제: 해당 행·열 제거, 추가 조회 0회.

역·날짜·검색 옵션·데이터 버전이 바뀌면 관련 항목의 유효성을 다시 판단한다. 허용되지 않은 크롤링 결과 재사용을 위 수치의 전제로 삼지 않는다. 가중치 수정 후 최적화에 필요한 대안이 기존 응답에 없으면 추가 데이터가 필요하다.
