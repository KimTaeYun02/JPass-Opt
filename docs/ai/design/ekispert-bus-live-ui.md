# 버스 실조회·좌표·프론트 재생 검증 계약

2026-11-14. 사용자가 이전에 제시한 실제 검색·정류장 좌표·프론트 연결 검증을 모두 요청했다.
현재 작업의 하위 프로세스로 Claude Opus의 읽기 전용 테스트 설계 계약을 받았다.

## 대상과 인터페이스

1. 일반 브라우저 UI에서 금각사도 → 기타오지 버스터미널을 운영사까지 명시해 검색한다.
2. 제품과 같은 `headless=False` 크롤러, `headless=True` 크롤러를 같은 입력·출발 시각으로 비교한다.
3. 실제 UI에 보이는 지도 버튼·URL에서 정류장 코드와 대표 좌표를 확인한다.
4. 정류장 대표 좌표로 Google WALK를 최대 2회 호출하고 기존 철도역 좌표 처리 함수도 확인한다.
5. 실제 프론트 어댑터·렌더러·지도 경로 변환 함수에 실측값을 조립한 테스트 응답을 전달한다.

## 불변조건

- 기존 제품 API·스키마·최적화 알고리즘·프론트 코드는 변경하지 않는다.
- 관측한 전체 정류장명·운영사를 보존하고, 웹 정류장 코드를 Google Place ID와 혼용하지 않는다.
- Google WALK는 실제 정류장 지도 좌표를 확인한 뒤 최대 2회, Gemini와 공식 Ekispert API는 0회다.
- 403·429를 받으면 해당 실행은 종료한다. 헤더 위조·차단 우회·재시도 루프를 넣지 않는다.
- 브라우저 UI는 컴퓨터 사용 도구, 제품 크롤러 검증은 기존 CLI를 사용한다.
- 실제 검색, 대표 좌표, 수동 대기시간, 테스트용 장소 ID, 재생 응답을 명시적으로 구분한다.
- 제품 최적화 API가 버스를 자동 연결한 종단 간 검증으로 보고하지 않는다.
- 코드·문서에는 키·쿠키·개인 위치·인증 로그를 넣지 않는다.

## 수용 기준과 검사

- 양쪽 운영사와 실제 선택된 이름을 기록하고 노선·시간·요금·웹 정류장 코드를 확인한다.
- 지도 버튼에서 대표 좌표가 확인되지 않으면 임의 좌표로 도보 실호출을 진행하지 않는다.
- 버스정류장 좌표 조회 실패와 정상 철도역 조회를 비교해 기존 서비스의 실패 위치를 특정한다.
- 재생 응답은 기존 Pydantic 응답 모델과 프론트 파서를 통과해야 한다.
- 실제 프론트 어댑터 → Vite 프록시 → 진단용 FastAPI 응답의 HTTP 전송을 검사한다.
- 도보/노선/도보 순서, 시간·요금 합계, 버스 노선명, 도보 경로 굴곡과 노선 연결선 표시를 확인한다.
- 발견한 실제 오류는 최소 변경으로 수정하고 회귀 검사·빌드·독립 검토를 완료한다.

## 회귀 위험과 한계

웹 지도 좌표는 정류장 대표점으로 승강장 위치·출입구를 보장하지 않는다.
현재 크롤러는 첫 자동완성 항목을 선택하므로 다른 운영사·일부 일치만으로 성공 처리하지 않는다.
현재 최적화는 고정 비용표를 사용하며 대기시간과 도보 이후의 실제 탑승 시각을 자동 재조회하지 않는다.
재생 화면에 대기 5분을 수동으로 포함하더라도 제품의 시간표 계산이 개선된 것은 아니다.
브라우저 모드에 따른 이번 접근 결과를 모든 서버 환경의 보장이나 403 원인 확정으로 해석하지 않는다.
